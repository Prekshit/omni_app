1) HIGH LEVEL SYSTEM ARCHITECTURE
============================================================

USER FLOW (OMNI VISUAL SEARCH)
1. User opens Flutter app -> Omni scanner screen.
2. User taps "Click" on Omni screen -> camera captures image.
3. Flutter sends multipart image to backend endpoint:
   OMNI_BACKEND_URL = http://<laptop-ip>:3000/api/visual-search
4. Backend uploads image to Supabase Storage bucket ("Omni").
5. Backend creates signed URL for uploaded image.
6. Backend calls SerpApi Google Lens (engine=google_lens, type=products).
7. Backend infers product query from top Lens titles.
8. Backend calls SerpApi Google Shopping (engine=google_shopping, q=inferredQuery).
9. Backend parses Lens + Shopping results -> normalizes product DTO.
10. Backend categorizes each product using domain map + heuristics:
    Local, Quick, Bulk, Global, Refurb, Other.
11. Backend scores and ranks products (brand/token/category boosts, penalties).
12. Backend groups top results by category and returns JSON to Flutter.
13. Flutter renders "Similar Products Found" bottom sheet:
    category rails + count + horizontal cards + arrow to category details page.

DATA + LOG FLOW
1. Raw provider responses are stored in backend/debug:
   - <requestId>-serpapi-lens-raw.json
   - <requestId>-serpapi-shopping-raw.json
2. Processed merged output is stored in backend/debug:
   - <requestId>-omni-products.json
3. Runtime server logs are appended in:
   - backend/omni-backend.log
4. Supabase temporary uploaded image is deleted in backend finally block.

4) BACKEND (backend/)
============================================================

backend/core files
- backend/server.js
  Main Node.js API server.
  Responsibilities:
  - Exposes /health and /api/visual-search.
  - Receives image upload using multer (memory storage).
  - Uploads image to Supabase and creates signed URL.
  - Calls SerpApi Lens and Shopping.
  - Parses, merges, deduplicates, categorizes, scores, and groups products.
  - Writes debug JSON and runtime logs.
  - Returns final API payload to Flutter.

- backend/package.json
  Backend package manifest (scripts and dependencies).

- backend/package-lock.json
  Locked backend dependency tree.

- backend/README.md
  Backend usage/setup + endpoint details.

- backend/.env
  Local secrets (not to commit):
  SERPAPI_KEY, SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, SUPABASE_BUCKET, etc.

- backend/.env.example
  Example env template.

- backend/omni-backend.log
  Append-only runtime log for request lifecycle and timing.

backend/config
- backend/config/categories.js
  Category definition list and display order:
  Local, Quick, Bulk, Global, Refurb, Other.

- backend/config/domainMap.js
  Curated domain -> category mapping used before heuristic fallback.
  Grows over time with observed commerce domains.

backend/runtime folders
- backend/debug/
  Stores per-request raw and processed JSON artifacts for QA/debug.

- backend/node_modules/
  Installed backend dependencies.

11) CURRENT OPERATIONAL NOTES
============================================================

1. Frontend code is currently centralized in `lib/main.dart` (non-modular by current team decision).
2. Backend is local-first for hackathon velocity; phone and laptop must be on same network.
3. For real-device testing, OMNI_BACKEND_URL must use current laptop IPv4 from ipconfig.
4. Debug JSON files are intentionally retained (no auto-delete) for iterative QA.
5. Domain mapping quality directly impacts category accuracy; keep extending `backend/config/domainMap.js`.

============================================================
12) API RESPONSE SHAPE (BACKEND -> FLUTTER)
============================================================

The `/api/visual-search` response includes:
- `products`: merged, scored product list
- `inferredQuery`: query generated from Lens
- `timingMs`: per-stage timings (upload, signed URL, lens, shopping, normalize, total)
- `categorySummary`: counts per category
- `sourceSummary`: source counts (lens/shopping/merged)
- `categories`: grouped category arrays used by bottom sheet rails

============================================================
13) QUICK TROUBLESHOOTING
============================================================

1. `Client SocketException`:
   Usually wrong backend IP/port or network isolation.
2. `RenderFlex overflow`:
   Usually fixed-size card/text constraints in Flutter widgets.
3. `EADDRINUSE:3000`:
   Another process already running backend on port 3000.
4. Slow result times:
   Commonly external API latency + network + Supabase signed URL time.
