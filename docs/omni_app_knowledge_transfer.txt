1. WHAT IS OMNI?
================================================================================

Omni is a mobile "scan and shop" application. The user points their phone camera
at any real-world product, taps a capture button, and within seconds sees a
categorized list of links to buy that product from multiple Indian and global
e-commerce platforms.

The app also features a mock "PhonePe Partner Checkout" experience. Selected
product cards are branded with a PhonePe logo; tapping them bypasses a third-
party browser and instead opens a polished in-app checkout page, a payment
success screen, and a downloadable/shareable invoice.

5. BACKEND ARCHITECTURE & REQUEST PIPELINE
================================================================================

Endpoint: POST /api/visual-search
  Input:   multipart/form-data with field name 'image'
  Output:  JSON with keys: products, categories, inferredQuery, querySource,
           timingMs, categorySummary, sourceSummary

Step-by-step pipeline for every scan request:

  STEP 1 – Receive & validate image
    Multer parses the multipart upload into req.file.buffer (in memory).
    A unique requestId (8-char UUID slice) is generated for log tracing.

  STEP 2 – Upload image to Supabase Storage
    Path: visual-search/{timestamp}-{uuid}.{ext}
    Timeout: 15 seconds
    Purpose: Google Lens API requires a publicly accessible URL, not raw bytes.
    Cleanup: The file is ALWAYS deleted from Supabase in the finally block,
             regardless of success or failure, to prevent storage bloat.

  STEP 3 – Generate a signed URL
    Supabase signed URL valid for 10 minutes (600 seconds).
    Timeout: 10 seconds.
    This URL is what gets passed to SerpApi Lens.

  STEP 4 – Call SerpApi Google Lens API
    URL: https://serpapi.com/search.json?engine=google_lens&type=products
    Timeout: 50 seconds (AbortController)
    Returns: shopping_results, visual_matches, exact_matches
    Parsed into a list of OmniProduct-shaped objects via parseLensProducts().

  STEP 5 – Infer the product search query (see Section 7)
    The top Lens results are analyzed to determine the best text query
    for a follow-up Google Shopping search.

  STEP 6 – Call SerpApi Google Shopping API (if inferredQuery is non-empty)
    URL: https://serpapi.com/search.json?engine=google_shopping&q=...
    Parameters: gl=in, hl=en, google_domain=google.co.in
    Timeout: 50 seconds
    Returns: shopping_results, featured_shopping_results, inline_shopping_results
    NOTE: Shopping API failure is non-fatal. If it fails, Lens results are used alone.

  STEP 7 – Merge products (deduplicate)
    Both result sets (Lens + Shopping) are merged using a composite key:
    normalizedTitle | domain | normalizedLink
    First-seen wins; duplicates are dropped.

  STEP 8 – Score all products (see Section 8)
    Each product gets a numeric relevance score based on multiple signals.
    Products are sorted descending by score, then by visualRank as tiebreaker.

  STEP 9 – Categorize and group
    Products are grouped into 6 ordered category buckets (see Section 9).
    Each category gets at most 25 products.

  STEP 10 – Debug snapshot
    Full request result (including all raw data) is written to debug/{requestId}-omni-products.json
    Raw SerpApi responses are also saved to debug/{requestId}-serpapi-lens-raw.json
    and debug/{requestId}-serpapi-shopping-raw.json

  STEP 11 – Return JSON response

Other endpoints:
  GET /health               Returns { ok: true }. Health check.
  GET /api/user-profile     Returns static pre-seeded user info for checkout demo.

7. PRODUCT QUERY INFERENCE (3-STAGE ALGORITHM)
================================================================================

Function: inferProductQuery(products, lensRawData)
Purpose: Derive the best possible text search query from Lens results to use
         for the follow-up Shopping API call.

The algorithm runs in 3 stages and returns as soon as a confident result is found:

  STAGE 1 – Exact Matches (highest confidence)
    Checks if lensRawData.exact_matches exists and has items.
    Takes the first exact match's title, cleans it with cleanProductTitle(),
    builds a query using buildQueryFromTitle(), and returns.
    Source tag: 'exact_match'

  STAGE 2 – Position-1 Anchor with brand confidence check
    Takes the title of the first Lens result (position 1).
    Cleans it with cleanProductTitle().
    Looks for a known brand token in the cleaned title using knownBrands set.

    HIGH CONFIDENCE: If position-2 also has the same brand token
      → Use cleaned position-1 title as query.
      Source tag: 'position1_high_confidence'

    MEDIUM CONFIDENCE: Brand found but position-2 has a different brand or absent
      → Use cleaned position-1 title as query.
      Source tag: 'position1_medium_confidence'

    NO BRAND but title is long enough (>5 chars after cleaning)
      → Use cleaned position-1 title directly.
      Source tag: 'position1_no_brand'

  STAGE 3 – Consensus Fallback (lowest confidence)
    Analyzes top 12 Lens products using position-weighted token scoring.
    Weight for product at index i: max(1, 12 - i)
    For each product, tokenizes title text and adds weight to each token's score.
    Stop words (queryStopWords) are excluded.
    Ranks tokens by total weighted score.
    Identifies a brand token among top-ranked.
    Returns: brand + top non-brand, non-accessory tokens (max 6 total).
    Source tag: 'consensus'

Title cleaning (cleanProductTitle):
  1. Strip leading "Domain.tld: Buy " or "Domain.tld: " prefixes.
  2. Strip trailing ": Domain.tld: ..." suffixes (marketplace name leakage).
  3. Strip trailing " - Domain.tld" suffixes.
  4. Strip trailing " | Category" suffixes.
  Result: clean product model name without marketplace pollution.

Query building (buildQueryFromTitle):
  Tokenizes the cleaned title, removes queryStopWords, takes first 6 tokens,
  joins with spaces.

queryStopWords includes: accessory terms (adapter, bag, cable, case, charger,
charging, cover, protector, skin, sleeve, stand) + marketplace names (amazon,
aliexpress, bestbuy, ebay, flipkart, meesho, myntra, snapdeal, walmart) + 
generic words (and, best, bluetooth, buy, compatible, electronics, for, free,
genuine, global, india, new, official, online, original, price, pro, sale,
shop, store, tws, true, wireless, with).

8. PRODUCT SCORING MATH (DETAILED)
================================================================================

Function: scoreProduct({ product, queryTokens, queryWithoutBrand, primaryBrand })
Returns: { score: number, reasons: string[] }

Base score:
  score = max(0, 42 - product.visualRank)
  → Products at rank 1 start at 41, rank 42+ start at 0.
  → This rewards products the Lens API naturally placed higher.

Query token bonus (+12 per token):
  For each token in queryTokens:
    If the token appears in the product's combined text (title + source + domain):
      score += 12

Full model match bonus (+18):
  If queryWithoutBrand has ≥ 2 tokens AND all of them appear in the product text:
    score += 18
  → Rewards products that match all non-brand query terms (the model number/name).

Brand match bonus (+18):
  If primaryBrand is found AND it appears in the product text:
    score += 18

Different brand penalty (-35):
  If primaryBrand is set AND the product text contains a DIFFERENT known brand:
    score -= 35
  → Strongly penalizes competitor brand results.

Accessory penalty (-24):
  If the product text contains an accessory term (case, charger, cable, etc.)
  AND the original query did NOT ask for an accessory:
    score -= 24
  → Prevents phone cases appearing when scanning a phone.

Category boost:
  indian_ecommerce:  +14
  quick_commerce:    +13
  bulk:              +8
  international:     +4
  second_hand:       +3
  other:             +0
  → Biases results toward Indian local retailers (better UX for India).

Data completeness bonuses:
  Has image:  +3
  Has price:  +3

Final sort:
  Primary:   descending relevanceScore
  Tiebreak:  ascending visualRank (original Lens API position)

9. PRODUCT CATEGORIZATION LOGIC
================================================================================

Function: categorizeProduct({ domain, source, title })
Returns: { categoryId, reason }

Categories (in UI display order):
  ID                 UI Title    Priority
  ─────────────────────────────────────────
  indian_ecommerce   Local       1
  quick_commerce     Quick       2
  bulk               B2B         3
  international      Global      4
  second_hand        Refurb      5
  other              Other       6

Categorization runs these checks in order (first match wins):

  1. Direct domain map lookup
     domainCategoryMap[domain] → immediate return if found
     Covers ~650 explicitly curated domains.

  2. Parent domain lookup
     For domain "shop.amazon.in", tries "amazon.in" and "in" as parent domains.
     Returns if any parent is in domainCategoryMap.

  3. Heuristic: Second-hand detection
     Matches specific second-hand domains + text signals:
     ("used", "pre-owned", "refurbished", "renewed", "second hand", "resale")

  4. Heuristic: B2B/Bulk detection
     Matches specific B2B domains + text signals:
     ("wholesale", "bulk", "supplier", "b2b", "manufacturer", "distributor")

  5. Heuristic: Quick Commerce detection
     Matches specific quick-delivery domains + text signals:
     ("instamart", "zepto", "blinkit", "bigbasket", "dunzo", "jiomart",
      "dmart", "quicksnick", "quick delivery", "minutes", "10 minute", "same day")

  6. Heuristic: Global Marketplace detection
     Matches global domain patterns (amazon., ebay., aliexpress., etc.) + signals:
     ("global shipping", "international", "mercado libre", "ebay", "ozon")

  7. Heuristic: India TLD
     If domain ends with ".in" or ".co.in" → indian_ecommerce

  8. Fallback
     category: 'other', reason: 'fallback:other'

SPECIAL CASE – Google Proxy Links:
  SerpApi Shopping results sometimes return domain = "google.co.in" (a Google
  comparison page, not the actual seller). The server detects this:
  If domain.includes('google.') AND the item's source field looks like a domain
  (contains '.', no spaces, no slashes) → use source as the true domain.
  This prevents Indian retailers from being misclassified as Local due to
  the India TLD heuristic on a Google domain.

11. DEDUPLICATION & MERGING LOGIC
================================================================================

Product deduplication uses a composite key:
  key = normalizedTitle + "|" + domain + "|" + normalizedLink

  normalizedTitle: lowercase, non-alphanumeric replaced with spaces, trimmed.
  normalizedLink:  URL parsed to remove query params and hash, lowercased.

Within a single SerpApi response (parseSearchProducts):
  Key = title + "|" + shoppingLink (simpler, pre-normalization)

Merge order (mergeProducts):
  Lens products are added first.
  Shopping products are added after.
  First occurrence of any key wins → Lens takes priority for ordering.

Per-response deduplication (parseLensProducts / parseShoppingProducts):
  Products with no title or no shoppingLink are dropped entirely.

14. PHONEPE PARTNER CHECKOUT FEATURE
================================================================================

This is a DEMO/MOCK feature for presentation purposes. It simulates what a
"PhonePe Partner Checkout" integration would look like.

--- WHICH PRODUCTS GET THE PHONEPE BADGE ---

Function: isProductPhonePeEnabled(OmniProduct product, List<OmniProduct> categoryProducts)

Logic:
  - Products in category 'other' are NEVER branded. (return false)
  - The branded count is determined DETERMINISTICALLY using the category ID's hash:
      seed = product.categoryId.hashCode
  - For 'indian_ecommerce' (Local tab):
      Only indices 0–4 are eligible (max 5 cards examined).
      count = 2 + (seed.abs() % 4)  → always between 2 and 5
      Product is branded if: index < count
  - For all other categories:
      Only indices 0–2 are eligible (max 3 cards examined).
      count = 1 + (seed.abs() % 3)  → always between 1 and 3
      Product is branded if: index < count

  KEY DESIGN DECISION: The seed is based on categoryId (not product data), so
  the count is FIXED per category across the entire session. This ensures the
  SAME products are branded in both the horizontal rail (bottom sheet) and the
  grid view (full category page). The UI is always consistent.

--- VISUAL BADGE ---

A circular purple container (Color 0xFF5F259F, PhonePe brand purple) is overlaid
on the top-right corner of the product's image using a Stack widget.
Inside it, the Devanagari text 'पे' is shown in white, simulating the PhonePe logo.
Badge diameter: 22px

--- CARD BEHAVIOR ---

PhonePe-branded card tapped:
  → Navigator.push → PhonePeCheckoutScreen(product: product)

Normal (unbranded) card tapped:
  → _nativeChannel.invokeMethod('launchUrl', {'url': product.shoppingLink})
  → Android: Intent.createChooser(ACTION_VIEW) → native browser chooser dialog

--- CHECKOUT SCREEN (PhonePeCheckoutScreen) ---

Theme: White background, deep plum (#360816) app bar.

On load:
  1. Calculates delivery time based on categoryId (deterministic using title hash):
       quick_commerce:   15 + (hash % 45) minutes
       indian_ecommerce / second_hand: 2 + (hash % 6) days
       bulk:             7 + (hash % 9) days
       international:    15 + (hash % 16) days
       other:            4 days (default)

  2. Fetches user profile from backend:
       GET /api/user-profile (4s timeout)
       Response: { name, address, contact, creditCard }
       Falls back to hardcoded values if unreachable.

  3. Initialises quantity = 1.

UI sections:
  - Delivery Address (name, address, phone from fetched profile)
  - Product Details card:
      image, title, per-unit price, category chip
      Quantity counter: dark-plum circular [-] / [+] buttons flanking the quantity
      number. Range: 1–99. Minus button disabled (greyed) at qty = 1.
  - Estimated Delivery card
  - Payment options (RadioListTile list):
      PhonePe UPI
      PhonePe Wallet
      UPI Lite             ← DISABLED (greyed, unselectable) when unit price > ₹2,000.
                             Shows sub-label: "Not available above ₹2,000".
      PhonePe Credit Card • 1007  ← default selected
  - "Pay Total: ₹X (N items)" elevated button
      Total = _parsePrice(product.price) × quantity
      "(N items)" suffix is shown only when quantity > 1.

UPI Lite disabling logic:
  _isUpiLiteDisabled = (_parsePrice(widget.product.price) * quantity) > 2000
  Threshold is based on the TOTAL order amount (unit price × quantity), NOT just
  the unit price. So a ₹1,100 item at quantity 2 (₹2,200 total) will grey out UPI Lite.
  _parsePrice strips all non-digit/non-period characters, then tries double.parse.
  When disabled: Opacity(0.5) wrapper, grey background card, onChanged = null.
  The disabled check is re-evaluated on every setState (qty change), so the tile
  re-enables or disables live as the user changes quantity.

Quantity counter:
  State variable: int quantity = 1  (per-session, resets on new checkout)
  _qtyButton: 30×30 circle, plum when active, grey.shade200 when at limit.
  _totalPrice getter: unit × quantity formatted as ₹X (no decimals for whole numbers).

Data passed to downstream screens on pay:
  PaymentSuccessScreen receives: product, deliveryTime, paymentMethod, name,
    address, contact, totalPrice (String), quantity (int)
  InvoiceScreen receives: same set
  Both screens use totalPrice everywhere price is displayed (Amount Paid, TOTAL PAID,
  ORDER DETAILS price column). When quantity > 1, invoice also shows a grey
  sub-line: "Qty: N × ₹unit" below the product source.
  Share text also includes the "Qty: N × unit" line when qty > 1.

Paying:
  Sets isProcessingPayment = true → shows 2.2s overlay.
  After delay → Navigator.pushReplacement → PaymentSuccessScreen

--- PAYMENT SUCCESS SCREEN ---

Shows:
  - Large circular badge in PhonePe Purple (#5F259F) with a white checkmark
  - "Payment Successful" title in PhonePe Purple
  - Summary card: Amount Paid, Transaction ID (TXN + epoch timestamp suffix),

15. DYNAMIC PRICING ALGORITHM (FOR MISSING PRICES)
================================================================================

Problem: Amazon.in listings (and some others) do not expose prices in SerpApi
Lens results. PhonePe-branded cards with no price look broken at checkout.

Solution: A post-processing step that fills in estimated prices for unpriced
PhonePe-branded products, using other products in the same category as reference.

Function: _fillMissingPhonePePrices(List<OmniCategory> categories)
Called in: captureAndSearchProducts(), after parsing and before returning results.

Algorithm (runs once per category/tab):

  STEP 1 – Identify PhonePe products with missing prices:
    For each product: isProductPhonePeEnabled() && !_hasPriceFetched()
    _hasPriceFetched() returns true if price is non-empty and parseable as double.

  STEP 2 – Collect all successfully fetched prices in the tab:
    fetchedPrices = all products where _hasPriceFetched() is true, parsed as double.

  STEP 3 – Compute average:
    If fetchedPrices is non-empty:
      avgPrice = sum(fetchedPrices) / count(fetchedPrices)
    Else (no prices at all in the tab):
      avgPrice = 1000.0 + Random().nextInt(9001)  → random between 1000 and 10000

  STEP 4 – Assign prices with discount:
    If exactly 1 PhonePe product is missing a price:
      discountPct = 0.12  (fixed 12% discount)
    If 2 or more PhonePe products are missing prices:
      discountPct = Random().nextDouble() * 0.15  (random 0% to 15% each)

    calculatedPrice = avgPrice * (1.0 - discountPct)
    formattedPrice  = "₹" + calculatedPrice.toStringAsFixed(0)
    Product gets: product.copyWith(price: formattedPrice)

  Products that already have prices are NOT modified.
  Categories with no unpriced PhonePe products are returned unchanged.

Math summary:
  Single card: price = avg - (avg × 0.12) = avg × 0.88
  Multiple cards: price = avg - (avg × rand[0, 0.15]) = avg × rand[0.85, 1.00]
  No prices in tab: avg = rand[1000, 10000], then apply above formula.

Price parser (_parsePriceToDouble):
  Strips all non-digit, non-period characters from the price string.
  Tries to parse the resulting string as a double.
  Returns null on failure.

File: android/app/src/main/kotlin/com/example/omni_app/MainActivity.kt
Channel: com.example.omni_app/native

Three methods are registered:

  1. launchUrl
     Arguments: { url: String }
     Action: Creates ACTION_VIEW Intent with the URL, wraps in Intent.createChooser
             ("Open with browser"), starts the chooser activity.
     Used: When a non-PhonePe product card is tapped.

  2. shareInvoice
     Arguments: { text: String }
     Action: Creates ACTION_SEND Intent (type: text/plain), sets EXTRA_SUBJECT
             ("Omni Order Invoice") and EXTRA_TEXT, wraps in chooser
             ("Share Invoice via"), starts activity.
     Used: "Share Invoice" button on InvoiceScreen.

  3. saveImageToDownloads
     Arguments: { bytes: ByteArray, fileName: String }
     Action (Android 10+ / API 29+):
       Uses MediaStore.Downloads API:
       - Creates ContentValues with DISPLAY_NAME, MIME_TYPE (image/png),
         RELATIVE_PATH (Downloads), IS_PENDING = 1
       - Inserts into MediaStore.Downloads.EXTERNAL_CONTENT_URI
       - Opens output stream and writes bytes
       - Sets IS_PENDING = 0 to finalize
       No storage permission required on Android 10+.
     Action (Android < 10):
       Writes to Environment.getExternalStoragePublicDirectory(DIRECTORY_DOWNLOADS)
       directly via File.writeBytes().
     Used: "Download" button on InvoiceScreen.

19. KNOWN LIMITATIONS & FUTURE WORK
================================================================================

KNOWN LIMITATIONS

  1. Amazon.in Pricing:
     SerpApi Lens does not return prices for most Amazon.in listings.
     Current workaround: Dynamic pricing algorithm (Section 15) generates an
     estimated price for PhonePe-branded Amazon cards.

  2. Single File Frontend:
     All Flutter code (models, screens, widgets) is in one ~3150-line main.dart.
     Should be split into feature-organized files/packages for production.

  3. PhonePe Checkout is a Demo:
     The checkout flow does NOT actually process payments. It is a UI simulation.
     User profile data is hardcoded in the backend. Payment processing is fake.

  4. No User Authentication:
     There is no login, session management, or user-specific data persistence.

  5. Lens Accuracy:
     Google Lens product recognition is not perfect. Unusual or rare products
     may produce poor or irrelevant results.

  6. Google Proxy Links:
     Some Shopping results return google.co.in as the domain. The server uses
     the item.source field as a fallback domain in these cases, but source
     text is not always a clean domain and may still be misclassified.

  7. Category Heuristics:
     The text-based heuristics (isSecondHandResult, isBulkResult, etc.) are
     keyword-dependent and may misclassify products whose titles happen to
     contain heuristic keywords (e.g. a product called "International Brand X"
     could be misclassified as Global).

  8. Single Backend / No Caching:
     Every scan triggers two fresh SerpApi calls. There is no result caching.
     High-frequency usage will rapidly exhaust the SerpApi quota.

  9. Quantity is Session-Local:
     The quantity counter in the checkout screen is in-memory only. It resets
     to 1 every time the checkout screen is opened. There is no cart persistence.

POTENTIAL FUTURE IMPROVEMENTS

  - Split main.dart into separate files (models/, screens/, widgets/, services/)
  - Add real caching (Redis or in-memory LRU) for repeated product scans
  - Replace PhonePe demo checkout with a real PhonePe SDK integration
  - Persist cart/quantity across sessions (Supabase or local SQLite)
  - Add product detail page with price history graphs
  - Add user favorites / scan history (Supabase or local SQLite)
  - Replace domainMap.js with a database-backed admin UI for easier maintenance
  - Add ML-based re-ranking to improve product relevance beyond score heuristics
  - Support multiple languages / regions (currently India-only biased)
